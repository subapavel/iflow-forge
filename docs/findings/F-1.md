# F-1 — `Participant` carries no endpoint and no adapter configuration

Date: 2026-10-19 · Task: KB-02 · Spec: docs/superpowers/plans/2026-10-19-pipeline-knowledge-base.md, Task 2 Interfaces
(plan line 88); spec §6 (the `po-xray iflow` dump is the reading surface for the pages, CLAUDE.md "never load an `.iflw`
file whole")

- **Assumption in the document:** `record Participant(String name, String componentType, String direction)` — from each
  `bpmn2:messageFlow`: `Name`, `ComponentType`, `direction` — is enough of the adapter side for the pages.
- **How it fails in practice:** the first dump of `generic-pipelines` prints participant lines such as
  `- participant: JMS JMS Receiver` ten times per iFlow: the message-flow `Name` is often just the adapter type, the endpoint
  participant's name (`InterfaceDeterminationQueue`, `DeadLetterQueue`) and the adapter configuration (`QueueName_outbound`,
  ProcessDirect `address`, `{{Param}}` references) are not in the record. KB-04's "Adapters" and "Externalized parameters"
  sections cannot be written from the dump, and the `.iflw` may not be loaded whole; the kb-author would have to grep raw
  XML for every adapter, uncited and unchecked.
- **Severity:** major (a documented mechanism — the dump as reading surface — would not serve its purpose; the intent is kept
  by widening the record).
- **Evidence:** target/kb-02-smoke.log lines 2–11 (ten `- participant: JMS JMS Receiver` / `ProcessDirect ProcessDirect
  Receiver` lines for step02.inbound.processing); PIP_04_Generic_ReceiverDetermination.iflw messageFlow
  `MessageFlow_51071382` (properties ComponentType=JMS, Name=JMS_OuboundProcessing, direction=Receiver, QueueName_outbound…,
  targetRef=Participant_51071380 whose `name` is the endpoint).
- **Change made:** `record Participant(String name, String componentType, String direction, String endpoint,
  Map<String, String> properties)` — `endpoint` = the `name` attribute of the `bpmn2:participant` the message flow connects
  to (its `sourceRef` for a Sender, its `targetRef` for a Receiver; `""` when unresolved), `properties` = every
  `ifl:property` pair of the message flow in document order (the `.iflw` holds SAP defaults and `{{Param}}` references, no
  tenant values — spec §13.2). Markdown dump line becomes `- participant: <name> <componentType> <direction> -> <endpoint>`;
  the properties appear in the JSON dump only (the Markdown stays the compact overview, JSON the lossless surface, as for
  steps). Everything else as designed.
- **Spec edit:** plan changelog line at the top (2026-10-19, F-1, Participant widened) and the Interfaces bullet rewritten.
- **PROGRESS entry:** KB-02 marked `Deviation: F-1`.
- **For the owner's review:** whether the adapter configuration should also be rendered in Markdown (rejected for now: ~20
  properties × ~10 flows per generic iFlow would triple the dump; `--json` carries them).
