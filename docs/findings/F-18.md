# F-18 — AdapterMessageMonitoring on QA: what the live read calls settled

Date: 2026-11-11 · Task: MON-07 · Spec: `docs/superpowers/specs/2026-11-11-message-monitoring-design.md` §9 ·
builds on F-17

- **Assumption in the document:** §9 left open the accepted `status` values, `dateType`, the
  payload `version` and `logLocations`, and whether a search without a time window is accepted;
  F-17 (owner's review item 1) asked whether the eight required `AdapterFilter` fields sent as
  false/0 narrow a search. MON-02..06 assumed the Locale with three children, a message key usable
  as given, and — in the default payload part of MON-05 (CLI) and MON-06 (MCP) — that with more
  than one part, part 0 is the XI header and part 1 the main document.
- **How it behaves in practice:** every intended read call of the acceptance run succeeded on QA
  under the owner's configured user: no authorisation error, so the user's roles were sufficient
  for all operations called. Point by point:
  - **Message status values:** `getAllAvailableStatusDetails` returns 186 lines of numeric
    status-detail codes with error texts — not the message statuses. Message statuses seen in
    results: `canceled`, `delivering`, `success`. `--status canceled` returned 9 messages;
    `--status systemError` returned 0 without a fault; an invented status value returns a SOAP
    fault (HTTP 500, `EJBException`), shown by the CLI as a one-line error with exit 1. So the
    server validates the value and `systemError` is a known one. `--faulty` returned the same 9
    messages as `--status canceled` in this 7-day window.
  - **Required filter defaults:** all 9 faulty messages carry `wasEdited=true` although the filter
    sends `wasEdited=false`, so that default does not narrow. `timesFailed` and `retries` were 0 on
    all 59 messages seen, and the messages carry no `archive` field, so the `timesFailed`,
    `retries`, `archive`, `nodeId` and `retryInterval` defaults are **not decided**: searches with
    them return messages, but whether they exclude some is not visible.
  - **`dateType`:** not exposed by the CLI or MCP (always 0); **not decided**.
  - **Time window:** `--from` without `--to` is accepted. A search with no window at all was not
    tried (the CLI always sends one, §9 architect's call); **not decided**.
  - **Message key:** six parts separated by a backslash; usable as given by `log`, `payload` and
    `uds-attributes`.
  - **Audit log:** entries carry `timeStamp`, `status`, `textKey`, `params`, `localizedText`; the
    answer has no `version` or `logLocations` field, so the log does not tell which values to use.
  - **Payload `version`:** 0, 1, 2 and 3 are all accepted and return content identical to the
    current payload for the message probed. **Meaning not decided.**
  - **Logged payload `logLocations`:** `AM` returns content identical to the current payload, `MS`
    a different one (176 B instead of 163 B), `BI` an empty answer ("no payload") without a fault.
  - **XI header part:** 40 messages read with `getMessageBytes` (all 59 distinct IDs seen, first 40)
    each returned one part — the application document (`application/xml` 27, `text/xml` 13,
    content-id of the form `payload-<uuid>@sap.com`); no XI header part came back. A message with an
    attachment was not seen. **Contradiction:** the default-part rule of MON-05/06 (`parts > 1` →
    part 1) assumes part 0 is the XI header; on a message with an attachment it would most likely
    skip the main document. Row MON-08 replaces the positional rule (red test first).
  - **Locale:** `lookup status-details --lang en` with the three Locale children caused no fault.
  - **`getInterfaces`:** answers `<Response xsi:nil="true"/>` on QA, although interfaces exist (search
    and `uds-filters` return them). The tool reports 0 values and keeps the nil in `otherFields`
    with its "could not be mapped" note, as the honesty rule requires.
  - **User-defined search:** one interface has a search filter; `uds-attributes` of one of its
    messages returns one attribute; `uds-search` with that `name=value` returned 0 messages in the
    first run and 1 message in six later runs (operator AND, OR or none; with and without the
    interface filter; 7 and 30 days). The first 0 was not reproduced; cause unknown. AND and OR are
    both accepted.
  - **MCP:** over stdio the server lists the 11 `message_*` tools, `statuses` is declared as an
    array of strings, and `message_search` with `statuses` as a JSON array of one code and limit 5
    returned 1 message where the unfiltered 1-day search returns 5 — the array binds and is applied
    (MON-06 limit closed).
- **Severity:** minor for the settled points; the default-part rule is a defect (MON-08).
- **Evidence:** full outputs under `local/<customer>/monitoring-acceptance/` (gitignored); neutral
  run log `target/mon-07/run.log` (commands with placeholders, exit codes, counts). QA only, read
  operations only; no PROD or DEV call by an agent.
