## Purpose

Present source evidence side by side for explicitly aligned steps and every unmatched step.
Alignment is an attributed candidate/confirmed choice; it never proves semantic equivalence, execution,
delivery or successful import. No automatic name matching or semantic diff engine. Original P3/P4 reports
remain immutable evidence behind every cell. Facet values, not only links, must be readable in Markdown.

## Exact public interfaces

## Alignment and rows

Explicit alignment rows follow input order, IDs alignment:<original-index>; alignment field retains raw supplied ID.
Blank/duplicate alignment IDs are diagnostics, not overwritten data; row ordinal IDs stay unique.
Every row has exactly one cell per implementation, input order. Missing member ->state not-aligned, null step,
empty facets; never label it absent behavior. Valid member ->state source-step. Every present source step remains
a candidate source occurrence even when structural connectivity is unreachable/unknown.

Resolve StepRef only by exact case-sensitive unique implementation ID, unique ProcessKey and unique step ordinal
within its path process. No name, label or locator fallback. Blank/duplicate implementation IDs are diagnostics;
their source steps remain visible as unmatched by column ordinal. Null/missing reports are explicit unknown coverage.
Duplicate process keys/step ordinals are ambiguous references; retain their separate occurrences in unmatched rows.

Alignment status allowed candidate or confirmed. Both require at least one evidence entry with nonblank all4fields;
confirmed additionally requires at least one such entry with status confirmed. This validates supplied attribution,
not authenticity, owner authority or semantic correctness. Other statuses/missing evidence ->row status invalid.
All supplied evidence retained, invalid entries diagnosed. One step per implementation per row, no repeated members.
Any unresolved member, duplicate column, duplicate member or reused step across rows makes affected rows invalid;
check all rows before consuming steps so first row does not win a conflict. Invalid rows display resolved source
cells where possible with reason invalid-alignment, unresolved slots stay not-aligned; no step is consumed by invalid rows.
For duplicate column in an invalid row, do not choose a member: show not-aligned and diagnose original refs.
Diagnostics retain alignment ID/index, complete offending refs and evidence/status values.

Append all unused source occurrences in implementation/path-process/step list order as unmatched rows:
IDs unmatched:<implementation-index>:<process-list-index>:<step-list-index>, status unmatched, alignment null.
Only the owning column gets source-step; other columns not-aligned. Do not drop disconnected or repeated-name steps.
No alignment means all steps unmatched. Even an explicit confirmed alignment is displayed as supplied confirmation,
never an equivalence verdict. No numeric similarity score or automatic grouping is introduced.

## Facets and association rules

For every source-step emit all facet kinds in order: presence, conditions, data, loops, faults, calls, channels, contracts.
Presence state is available for the original path step. Other facets are candidate when at least one valid pointer
exists and no association defect/source reason is found. Unknown takes precedence for an empty facet, broken or
ambiguous association, unsupported facet version, or any selected source item's reasons. Keep all valid pointers
even when state unknown; union source reasons and explicit association diagnostics deterministically. Empty never
proves absence of runtime behavior. Unsupported unrelated facet versions do not suppress otherwise supported facets.
Stable pointer order follows source lists; duplicates removed by pointer equality preserving first occurrence.

- presence: path process step pointer (original name/kind/location/connectivity/witness/reasons).
- conditions: arcs in that process whose source or target endpoint candidate locators contain step.location;
  retain whole arc (condition/default/evidence), state candidate. Ambiguity is not pruned or interpreted false.
- data: uniquely matching ProcessData.key and StepState.step AND location; whole StepState pointer. Include
  declarations named by before/after OriginSet declaration ordinals, their MappingUse and associated Read entries;
  follow unique ordinal references only. This exposes values/default evidence and initial-role producers without
  inventing runtime availability. Unresolved IDs/references remain reasons; other data stays in Context.
- loops: only explicit host locator membership in current process; retain whole loop including mode/sequential,
  completion/condition, scope evidence and reasons. No inferred iteration count or execution.
- faults: same ProcessKey plus matching owner/event candidate locations; retain whole declaration, including scope.
  Scope containment alone never proves a step catches a fault. Unattributed declarations stay in Context.
- calls: uniquely matching ProcessWiring.key, StepCall.step and location; retain whole call as candidate.
- channels: through retained call.interfaces ->InterfaceUse.ordinal ->IcoMatch.ico ->integration.channelUses.ico
  ->candidate channel ordinals. Every InterfaceUse ordinal, IcoMatch.ico against integration.icos[].ordinal, and
  channel ordinal must resolve uniquely before following the next link. Retain the referring call/interface evidence,
  but dangling/ambiguous ICO must not bind channelUses on integer coincidence; ambiguous channel must not choose one.
  Retain interfaces/ICO matches, uniquely resolved ICO source, matching channelUses and channel configurations as
  candidates; no first-match or receiver-route certainty. Broken/duplicate references remain diagnostic/reasons.
  Process ingress/configuration not linked to a call remains context, not inferred step delivery.
- contracts: attach contracts only through explicit PortClaim.step or ValueClaim producer/consumer StepRefs
  matching current ProcessKey/step. First require catalog.data nonnull and equals behavior.data (full structural
  snapshot including source ancestry); otherwise no step attachment and diagnose ancestry mismatch when step
  claims exist. Numeric ProcessKey coincidence in unrelated reports cannot bind contracts. Source contracts without
  step refs stay context. Supplied status/evidence remains attributed, no approval propagation.

Data/fault process facets require unique exact process key plus matching nonnull original process dc/id/source;
missing/mismatch means unknown and context retention. Faults additionally require equal referenced Input entries
(ordinal,label,sha256) in fault and path reports for the process input; missing/duplicate/unequal entries suppress
step fault attachment. ProcessWiring has no independent dc/id/source: treat it only as embedded BehaviorReport
evidence, using unique key plus step/location; never claim independently verified wiring ancestry.
Duplicate path ProcessKey or step ordinal suppress ordinal-based data/calls/channels/contracts attachment for
all affected occurrences (unknown with reasons). Presence and exact-locator occurrence-local arcs/loops remain;
fault owner/event location attachment still requires unique process key and fault ancestry. Every occurrence is kept.
Locator associations stay exact; never names. Propagate input Issue lists
with implementation provenance rather than silently ignoring incomplete report evidence.

## Context and validation

One Context per implementation; retain available whole data, faults (including unattributed), integration,
process wiring and contracts as pointers tagged data-context/fault-context/configuration-context/wiring-context/
contract-context. Label explicitly implementation-level evidence, not attached to every step. Redundant context is
intentional so evidence not selected by conservative step associations is never lost.
Unsupported versions/null input, representable malformed members and missing required source structure produce
error diagnostics while retaining original implementations. Only comparison input1,BehaviorReport1,BpmDataReport1,
BpmPathReport1,BpmFaultReport1 and ContractCatalogReport1 are interpreted. Unsupported comparison input version
does not build rows; unsupported behavior/data/path version does not enumerate steps from that implementation.
Unsupported fault/catalog versions suppress only their step facets and retain raw Context evidence; other supported
facets remain available. Supported missing nested data means unknown coverage, never fabricated steps.
New comparison null entries must be diagnosed without NPE; embedded constructor failures at JSON binding follow read's IOException contract.

## Markdown and reading

Render a common row axis and implementation columns, supplied alignment status/evidence and unmatched rows.
Each cell shows each facet's state, original values selected by pointers, provenance pointers and reasons.
Show defaults, conditions/default arcs, loop flags, fault scopes, calls/channels and contract differences as
actual values; do not claim equal/unequal semantics merely from raw serialized equality. Render diagnostics
and implementation Context separately with actual selected values, labelled contextual/non-step-bound.
Escape pipe/newline content; repeated output deterministic. No truncation in core; MCP later uses existing spill.
Input file bytes unchanged by read, no external references followed. Unsupported versions are honest diagnostics.
