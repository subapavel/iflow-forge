### Sections and milestones

P1 propose scopes or section-declare introduce section IDs; repeated section-declare is invalid.
An unapproved planned section is sufficient to ask a question or plan its design work.
Milestone kinds: design, final-plan, specification, implementation, deployment, verification.
The following three sets define the milestone contract, without a second coverage boundary:

1. Declared parts: `sections`, a nonempty list of known section IDs. `scope` pins at most one
   Dependency per part, never a different section. Design may omit a revision so drafting can
   start; every other kind requires exactly one Dependency for every declared part.
2. Declared connections: `connections`, a possibly empty array of Dependency scopes with
   unique known section IDs. A connection may have its own section outside the declared parts.
   `connectionRationale` is nonblank, including why none apply. This is declared wiring, not
   machine-proven semantic completeness; final approval binds the exact declaration.
3. Effective sections: declared parts UNION connection section IDs. Every membership test
   below that says a milestone contains/covers a section uses this set: question dependencies,
   inventory coverage, assumptions, risks, applicable answer bases, classification and blockers.
   Every consumed connection therefore requires a current question inventory and its own
   dependencies to be clear. No membership/readiness rule may use only declared parts.

Readiness evaluates approved content from scope plus connections, and inventories/questions
from effective sections. The report preserves the two input lists; their union is derived.
`requires` is a possibly empty list of existing milestone IDs. Cycles/self-reference fail.
Latest valid declaration of a milestoneId wins, preserving first-introduction order; replacing
a definition invalidates its old approval and downstream approvals. Do not delete history.

### Questions

question-open ID is question ID. `topic` preserves blocking/version/conversion/naming or another
explicit topic; it never determines dependency. `sections` names known affected sections.
Classification is scoped, nonblocking or unclassified. Scoped requires nonempty dependencies;
each is exactly `{sectionId,neededByMilestoneId}`, a known affected section and an existing
milestone containing that section. Nonblocking requires empty dependencies and explicit
classificationSource/reason. Unclassified requires empty dependencies and never means clear.
Only unclassified may have empty sections: then its unknown scope prevents assessment of all
milestones. Otherwise unclassified affects just intersecting sections and their dependants.
Reclassification is append-only; it does not alter the factual answer or imply owner approval.
It explicitly lists the current affected sections, so an unclassified legacy question with
unknown scope can later receive a concrete scope. It cannot drop a section used by an accepted
assumption's outstanding verification dependency. Changed question scope invalidates a basis
that no longer has a matching affected section; it cannot silently detach an approved basis.
Milestone redeclaration cannot leave any existing question dependency referring to a removed
section; such a declaration is rejected atomically. Question-classify cannot invalidate an
already accepted assumption's verification dependency.

Every effective section of a v2 milestone needs current question-coverage, even in a fresh v2 dossier.
This event explicitly records the analysis inventory: known sections (nonempty), all currently
known questions affecting any of them (including unclassified questions with unknown scope),
responsible owner and evidence locator. questions may be empty only as an explicit evidenced
"no questions found" inventory. It is not approval or proof that no unknown fact exists.
Latest valid coverage wins per section, in first-introduction order. It is current only while
its recorded question set equals the applicable current question set; newly opened or moved
questions make the affected coverage stale. Missing/stale coverage means not-assessed,
never ready. Questions may still be open or unclassified within a current inventory; their
own blockers apply independently. Include current coverage event IDs in approvalInputs.
Reject a coverage event atomically if its questions omit or add a question outside its sections.
The coverage event's question list is the exact union for its sections; each per-section Coverage
projection retains only the applicable subset, so a multi-section inventory does not make
unrelated questions block or stale its neighbour.

An answer requires its evidence locator. First answer has replaces:null; a correction names
the exact latest answer ID. Do not delete old answers or accept a mismatched replacement.
This records an answer, not tenant observation. A deferred/unanswered question remains unknown.
Deferral records reason and named review event/date in reviewAt; it retains every dependency.
Reject deferral of an answered question (a correction is a new answer). There is no clock,
scheduler or automatic answer: checking the needed milestone is what activates the block.

### Assumptions, answer bases and accepted risks

Assumptions require owner and approvalSource plus exact proposed Dependency scopes and a
nonempty list of permitted design milestone IDs whose sections cover those scopes. The
verification milestone must exist, be a non-design kind and contain the same sections.
The assumption only excuses matching question/section dependencies for those named design
milestones. It never marks the question answered and never excuses technical verification.
It additionally creates a blocking dependency at verifyAtMilestoneId and downstream milestones.
An assumption cannot cover a section outside its question. Later actual answers supersede the
assumption as a basis; assumptions do not automatically become technical evidence.

scope-basis binds one exact proposed scope to a nonempty array of
`{questionId,resolutionEventId}` (unique question IDs). Each resolution is the question's
current answer, or an applicable accepted assumption for that scope. A question must affect
the section. Register once, before the first approval of that exact scope; any rebinding,
including after approval, is invalid. A new answer makes a basis consuming the old resolution
stale. Staleness propagates to derived documents consuming that scope (required error,
optional warning, existing P1 semantics). No silent approval transfer or content rewriting.
When a milestone relies on an answered/assumed question, its relevant required scope must
have a current basis for that resolution; otherwise its content is not complete. Design work
can still proceed to write that revision, but cannot claim approved complete content.

Narrow legacy exception: scope-basis-import may add a first basis to a still-active scope
already approved in a preserved v1 dossier, without asking for new consent merely for the
format change. legacyPath/legacySha256 identify a read-only immutable v1 snapshot, resolved
like other dossier evidence. It must share migrationId and its entire events array must be
an unchanged prefix before this import event. approval must be an approval event in that
snapshot covering the exact scope; the snapshot and its digest are checked on every run.
Only first answers (question-answer with replaces:null) may be imported, never assumptions
or corrections; evidenceSource locates the historical relationship between those answers
and that original approval. It is not a new approval. If both answer and approval dates are
known and comparable, an answer later than approval is rejected. Compare only compatible
date precision; unknown or mixed date/datetime precision is not silently converted to a precise time.
Unknown dates stay unknown,
and authenticity of the historical locator is not machine-proven. A previous basis or second
import is always rejected. Later answer replacement still makes this basis stale. A forged,
changed or non-prefix legacy snapshot gives error LEGACY_IMPORT_INVALID. Normal v2 scopes
cannot use this exception without the genuine matching v1 prefix and approval.

risk-detail enriches an earlier P1 risk-accepted event. It may be registered only once, with
exact scopes within the accepted risk's sections, nonempty milestones and questions, owner,
approval locator and limitations. Each listed question must affect the scope and the listed
milestones must cover it. `triggers` is a nonempty subset of new-evidence/requirement-change.
Only this explicit detail can waive the specified unresolved question/section at the named
milestones; the question remains unknown. A bare P1 risk never acts as an exception.
risk-reopen requires a nonblank new evidence locator and a trigger allowed by its detail;
phase-change or an empty/repeated reopening is invalid. Reopening removes the exception;
reacceptance needs a new risk ID and approval. A milestone transition itself changes no risk.
Clarification during implementation: an explicit matching risk-detail may waive the question's
verification dependency created by an assumption, at that exact named milestone and scope only.
The assumption itself never waives verification; the fact remains unknown and the risk exception
is visible. The waiver does not transfer downstream. Reopening restores the block.

## Assessment and approval binding

Readiness is evaluated per milestone, including its explicit prerequisite graph. Inherited
blocking questions and unclassified dependencies remain visible. An exception applies only
to its named milestone and exact scope; it never spreads merely through a predecessor.
An open scoped question blocks only affected sections at its neededBy milestone and downstream
milestones. A design milestone for independent section B remains available while A waits.

`canWork`: dossier valid, question coverage current, dependencies classified/answered or explicitly excused for this
milestone, and required predecessor milestones ready. Missing scope approvals/bases alone do
not prevent design work. For other kinds, canWork also requires complete approved scope content.
`complete`: the dependencies above are clear and all required scopes/connections are active,
approved and current (including snapshot integrity and answer bases). A design milestone
with no selected revision can allow work but is not complete.
`approved`: a current milestone-approve event binds the current definition and exact inputs.
`ready`: canWork for design, complete for verification, complete+approved for final-plan,
and complete plus a ready final-plan ancestor for specification/implementation/deployment.
That ancestor must cover every exact required scope and connection of the target milestone
(decisionId/sectionId/revision/digest), not merely share a graph edge or section name. Multiple
unrelated partial plans cannot be combined to invent a whole-plan approval. Test final-plan
A versus implementation B, and final-plan A/r1 versus implementation A/r2: neither is ready.
The final-plan ancestor requirement cannot be bypassed by a partial section approval.
No value means authorization to deploy or operate a tenant.

The report exposes `approvalInputs` in deterministic order: current definition event IDs
through the prerequisite graph; approval event IDs for consumed scopes/connections; consumed
scope-basis event IDs; latest question classification event ID (open until reclassified) for
every applicable question; its current answer or the exact exception event used; and current
prerequisite milestone approval IDs where present. Deduplicate preserving first encounter.
A milestone-approve event's inputs must match this complete set (array order irrelevant,
duplicates invalid), definition must be its current declaration, and content must be complete
at that event. Later changes to any consumed input invalidate approval; unrelated next-action
or an unrelated section's answer does not. Approval cannot make incomplete content complete.
Reapproval is explicit and retains earlier approval events. Report the latest applied approval
event ID even when stale; approved=false and a blocker explain its status.

Readiness blockers do not themselves add dossier error diagnostics. Codes include
QUESTION_OPEN, UNCLASSIFIED_QUESTION, QUESTION_COVERAGE_MISSING, QUESTION_COVERAGE_STALE, SCOPE_NOT_APPROVED, STALE_BASIS,
PREREQUISITE_NOT_READY, CONNECTION_NOT_APPROVED, FINAL_APPROVAL_REQUIRED,
FINAL_PLAN_REQUIRED, INVALID_DOSSIER. Invalid events/references use existing error codes;
milestone cycles use MILESTONE_CYCLE; stale bases emit warning ANSWER_BASIS_CHANGED.
Invalid dossier assessments cannot affirm canWork/complete/approved/ready.
V1 assessment has status not-assessed and empty new lists; it never grants readiness.
