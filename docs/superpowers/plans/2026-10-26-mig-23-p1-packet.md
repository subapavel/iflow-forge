## 2. Veřejné rozhraní

Balík `io.poxray.migration`:

- `DossierValidator.check(Path dossier)` a `check(Path dossier, Path baseline)`
  vrací `DossierReport`, deklarují `throws IOException`; null baseline znamená
  bez porovnání historie. Metody jsou public static.
- `DossierValidator.markdown(DossierReport report)` vrací String, public static.
- `DossierReader` je interní helper (package-private), bez veřejného input modelu;
  načte úplný JSON strom, kontroluje duplicitní klíče a tvar, neztrácí pole.
- `DossierReport` je public record s poli v pořadí:
  `int formatVersion, String migrationId, String ledgerSha256, boolean valid,
  String historyStatus, List<Decision> decisions, List<Risk> risks,
  List<DerivedDocument> derivedDocuments, String nextAction, List<Diagnostic> diagnostics`.
- Nested public records:
  `Scope(String sectionId, String revision, String path, String sha256)`;
  `Decision(String id, String status, String text, String source,
  List<Scope> proposedScopes, List<Scope> activeScopes, List<String> approvalEventIds)`;
  `Risk(String id, String text, String source, List<String> sections)`;
  `Dependency(String decisionId, String sectionId, String revision, String sha256)`;
  `DerivedDocument(String id, String path, String status, boolean required,
  List<Dependency> consumes)`;
  `Diagnostic(String severity, String code, String eventId, String message)`.

Seznamy jsou immutable snapshots, prázdné seznamy se serializují jako `[]`,
ne chybějící/null pole. Vstup se nevyhodnocuje jako runtime evidence ani milestone readiness.

## 3. Formát dossieru v1

Root povoluje pouze `formatVersion` (integer 1), `migrationId` (M-kladné celé
číslo) a `events` (array). Jediný zdroj aktuálního stavu jsou tyto události.
Neznámé pole, duplicitní JSON key, duplicitní event ID, chybný typ nebo chybějící
povinné pole nejsou ignorovány ani převáděny výchozí hodnotou.

Každá událost má `id`, `type`, `at`, `source`: neprázdné strings; `at` je ISO
datum nebo ISO čas s offsetem nebo doslovné `unknown`. Zdroj je lokátor odpovědi
nebo podkladu, nikoli samotné oprávnění. Povolená další pole podle typu:

| type | Další pole | Význam |
|---|---|---|
| propose | text, scope | id události je decision ID; scope je neprázdný seznam Scope |
| approve | decision, scope | decision odkazuje na předchozí propose; scope je explicitní neprázdná podmnožina jeho přesných Scope |
| reject / defer / approval-unresolved | decision | Stav dosud neschváleného návrhu; neuděluje souhlas |
| supersede | decision, replaces, sections | Předchozí schválený nástupce, staré decision ID a neprázdný seznam section IDs, kde náhrada platí |
| risk-accepted | text, sections | Samostatné riziko, nikoli approval nebo odpověď na otázku; sections jsou známé section IDs |
| derived-document | documentId, path, required, consumes | Registrace odvozeného dokumentu; consumes je neprázdný seznam Dependency |
| next-action | text | Nejnovější platná taková událost určuje stručný další krok |

Scope má přesně `sectionId, revision, path, sha256` (neprázdné strings;
SHA-256 má 64 hex znaků). V jednom scope seznamu nejvýše jednou dané sectionId.
Stejné sectionId+revision musí napříč dossierem označovat stejný path/digest;
jiný obsah vyžaduje novou revizi. Hex porovnání hashů je case-insensitive.
Dependency má přesně `decisionId, sectionId, revision, sha256`.
Path je lokální file path; relativní vůči adresáři aktuálního dossieru.
Absolutní path je povolen pro existující externí soukromé podklady. Žádné URL
stahování ani zápis. Report nesmí přetiskovat payload podkladu do diagnostiky.

### Projekce a přechody

Události se čtou v pořadí pole, ne podle času; unknown data jsou legitimní.
Reference musí mířit na již existující správný typ události/rozhodnutí.
`approve` potvrzuje pouze vyjmenované Scope, nesmí rozšířit proposal ani
přenést souhlas na novou revizi. Opakované potvrzení stejného aktivního scope
je povoleno a přidá approval event ID; neobnoví již superseded scope.

Nástupce může být approved před supersede; finální konflikt se vyhodnotí po
celé historii. Supersede požaduje v daném okamžiku schválený scope starého i
nového rozhodnutí pro každou uvedenou sekci, odstraní pouze starý activeScope.
Nesmí obnovit dříve nahrazený scope, odkazovat na sebe nebo tvořit cyklus.
Bez explicitního supersede jsou dva aktivní decision IDs pro stejnou sekci
konflikt i při totožném obsahu. Návrh nástupce sám nic neruší.

Status rozhodnutí: proposed, deferred, rejected, approval-unresolved,
approved, partially-approved, superseded, partially-superseded.
Schválený/částečně schválený návrh nelze globálně reject/defer/unresolved;
změna schváleného obsahu potřebuje nový proposal a případnou náhradu.
Deferred/rejected/unresolved návrh může být později výslovně approved;
neznamená to doplnění technického důkazu.

Každý scope, který byl kdy schválen, odkazuje na archivovaný neměnný snapshot;
kontroluje se existence regular file a hash raw bytes i u později nahrazeného
rozhodnutí. Proposal ještě neuděluje schválení a jeho neověřený podklad se
nesmí prezentovat jako ověřený. Nečíst source lokátory jako soubory automaticky.

U derived-document vyhrává poslední registrace stejného documentId, historie
starších registrací zůstává. Stav missing, stale nebo current. Current vyžaduje
existující soubor a každý consumes odkaz na aktuálně aktivní schválený scope
s přesnou revizí a hashem. Missing/stale required dokument je error, nepovinný
warning. Není to sémantická kontrola prózy. Vytvořený Markdown přehled nese
ledgerSha256, nepřidává se sám sobě jako autoritativní dependency.

P1 neinterpretuje otázky ani jejich závislosti. Markdown tuto hranici uvádí;
nezobrazí nezkontrolovaný milník jako připravený. Rizika pouze odděleně vypíše.

## 4. Baseline, validita a diagnostiky

Baseline vybírá volající explicitně `--baseline`; nikdy se nehledá nejnovější
soubor podle času. Doporučené soukromé umístění `snapshots/dossier-<revision>.json`;
CLI snapshot neukládá. Bez něj historyStatus = `not-checked` a warning
`HISTORY_NOT_CHECKED`. Validní dossier může mít tento warning; není to ověřená historie.

Baseline má stejný formatVersion a migrationId. Jeho celý events array musí
být strukturálně shodný prefix aktuálního events array: klíčové pořadí objektů
a whitespace nehraje roli, pořadí arrays a všechny hodnoty ano. Neznámá pole
jsou odmítnuta, neodstraněna při deserializaci. Baseline se nesmí zkrátit/změnit;
identické celé historie jsou platné. Relative snapshot paths baseline se
nepřepočítávají podle jeho umístění — srovnává se historie, filesystem podklady
se ověřují pouze vůči aktuálnímu dossieru.

historyStatus = `verified` při úspěšném prefixu, `changed` při odlišnosti a
`invalid-baseline` při chybném baseline/identitě. Předchozí platnost designu
ani pravost souhlasu tím není prokázána, pouze prefixová neměnnost.

`valid` znamená žádná error diagnostika. Required malformed input/unknown
format/schema: error `INVALID_DOCUMENT` / `UNSUPPORTED_FORMAT`;
duplicita ID `DUPLICATE_EVENT_ID`; chybný odkaz `INVALID_REFERENCE`;
chybný přechod `INVALID_TRANSITION`; nesoulad Scope `INVALID_SCOPE`;
konflikt `APPROVAL_CONFLICT`; cyklus `SUPERSESSION_CYCLE`;
chybějící snapshot `SNAPSHOT_MISSING`; hash `SNAPSHOT_CHANGED`;
derived `DERIVED_MISSING` / `DERIVED_STALE`; baseline
`HISTORY_CHANGED` / `INVALID_BASELINE`. Severity je `error` nebo `warning`.
Zprávy jsou stručné a deterministické, bez obsahu soukromých souborů.

Nečitelný či syntakticky vadný hlavní JSON a duplicitní JSON key vyvolá IOException;
CLI ho zachytí a selže bez stack trace. U parsovatelné neplatné struktury se
vrací invalid report; neplatná událost nesmí nepozorovaně udělit schválení.
Invalid Markdown jasně říká, že není autoritativním aktuálním návrhem.

## 5. CLI a serializace

`po-xray dossier-check <dossier.json> [--baseline <previous.json>] [--json]`.
Jeden required argument, standardní Aesh help, JSON flag bez hodnoty,
baseline string option. Exit 0 valid dossier (warnings viditelné), exit 1
invalid nebo IO/parse error. JSON stdout je report, Markdown stdout je projekce;
summary/errors stderr dle stávajících commandů, bez stack trace.

Report deterministicky zachová pořadí prvního zavedení decisions/risks/documents;
události a scopes drží vstupní pořadí, žádné nedeterministické HashMap pořadí.
Markdown má jasný status, migration ID, history status, ledger digest, současné
schválené scopes, ostatní návrhy/stavy, rizika, derived documents, next action
a diagnostiky. Escapovat pipes, line breaks a backticks, aby source text nemohl
zfalšovat tabulku. Duplicitní pole či tiché ztráty nepokrývá default Jackson 3:
vyžaduje explicitní strict parsing. Nepřepisovat singleton Json ani původní reporty.
Registrovat DossierReport a všech 6 nested report records pro native reflection.
