# iflow-forge, part 1: SAP Integration Suite pipeline knowledge base

Design, 2026-10-19. Status: reviewed, open questions answered, awaiting Pavol's approval.

## 1. Where this sits

po-xray is being extended into **iflow-forge**: a tool that produces SAP Integration Suite iFlows built on the
SAP *pipeline concept*, from two kinds of input:

- an existing SAP PO Integrated Configuration (ICO), read by the po-xray readers, and
- an existing Integration Suite iFlow (typically point-to-point, generated by SAP Migration Tooling or built by hand),
  to be rebuilt as pipeline scenario artifacts.

The whole tool has five parts. They are separate projects with separate designs; this document covers part 1 only.

| Part | What | Depends on |
|---|---|---|
| 1 | **Pipeline knowledge base** → agent skill (this document) | nothing |
| 2 | Tenant profile: per customer / per country parameters of their pipeline copy (package names, JMS queues, endpoints, naming conventions) | 1 |
| 3 | Integration Suite iFlow reader: iFlow zip → scenario model | 1 |
| 4 | Generator: scenario model + tenant profile → importable package (scenario iFlows, partner directory entries); renaming is a special case | 1, 2, 3 |
| 5 | Code conversion: PO adapter modules and Java mappings → Groovy or native Integration Suite steps; agent-driven, guided by recipes from 1 | 1 |

Architectural decisions already taken (not re-opened here):

- The spine of the tool is a **scenario specification** (sender, interface, receivers, routing, mappings, QoS, adapters).
  Both inputs produce it, the human approves a proposal built on it, the generator consumes it. The agent never
  hand-writes iFlow BPMN XML.
- Output is always an **importable package**. Pushing it through the tenant API is an optional last delivery step,
  because some customers (E.ON) do not grant API users; manual import must always work.
- One repository (po-xray, to be renamed iflow-forge), multi-module Maven, Java 25, one MCP server exposing both
  the PO readers and the new tools.
- Development moves to Claude Code cloud sessions. Those work from the GitHub repository only, so **customer data
  never enters the repository** and tests in the repository run on synthetic or anonymized fixtures. Verification
  against real E.ON data stays a local step.
- Knowledge is **files in git**, never chat history. The knowledge base grows after every migration
  (self-improvement, see §8).

## 2. Intent and why

Pavol has studied the SAP pipeline concept twice: version 1 iFlow by iFlow and script by script with Claude Code
(summarized in a Czech document), and the update to the next version with ChatGPT. The knowledge lives in two chat
histories and one document. Nothing can be built on it in that form: an agent asked to migrate an ICO today does not
know what the pipeline is, which generic iFlows exist, what they expect in headers and partner directory, or what a
scenario has to contribute.

Part 1 turns that into a knowledge base an agent loads when it works on a migration, and that a human can read and
maintain. It is the single part where Pavol's own understanding is irreplaceable; everything after it is code.

Why pipeline rather than what SAP Migration Tooling produces: SAP's migration generates stand-alone point-to-point
iFlows and does not use the generic XI / IDoc inbound and outbound iFlows at all. Customers that run the pipeline
(E.ON, per country) want scenarios wired into it, with only the scenario-specific pieces generated.

## 3. Goals, non-goals, anti-goals

Goals:

- An agent with the skill loaded, and nothing else, can explain how a message travels through the pipeline, name every
  generic iFlow and what it does, state the header / property / partner-directory contract between the steps, and say
  exactly which artifacts a new scenario has to contribute and which it must not touch.
- The knowledge base is derived from the **actual pipeline artifacts** on disk (the truth), enriched by the reasoning
  from the chats and the Czech document (the why). Every factual statement is traceable to an artifact.
- Versioned by SAP pipeline version, with an explicit diff between versions, so that the next SAP update is handled by
  diffing artifacts and updating files, not by a new chat.
- Shaped from the start for parts 2 to 5: tenant-specific values are placeholders, scenario contributions are listed
  as a checklist the generator can implement, code-conversion recipes have a home that starts nearly empty.
- Portable: plain Markdown. The skill wrapper is Claude-specific, the content is usable from ChatGPT or any other agent.

Non-goals (later parts):

- No tenant profiles with real values (part 2). The knowledge base defines the placeholder names a profile must fill.
- No code: no reader, no generator, no API client.
- No full conversion catalogue for PO modules (part 5 fills it; part 1 only seeds the structure with what is already
  known from the chats).

Anti-goals (would make this a failure even if it "works"):

- A rewrite of the chat transcripts into prose. Length is not value; the agent pays for every token it loads.
- Facts that come from a chat and were never checked against the artifacts. A confident wrong statement about a
  header name costs more than a gap.
- Knowledge frozen at version 1 with version 2 as an appendix. The current version is primary; older versions are
  history.
- Customer data (E.ON queue names, URLs, package names) anywhere in the knowledge base.

## 4. Constraints

- Repository will be public or at least synced to GitHub for cloud sessions; treat it as public.
- SAP standard pipeline packages are downloadable content. Whether their unpacked sources may be committed depends on
  the repository's visibility and SAP's terms; see open question in §10. The knowledge base must be useful without
  them being in git (it cites paths inside the package, which anyone can download).
- The Czech document and chat exports are inputs only; they are not committed.
- Language of the knowledge base: **English** (my call). SAP terminology, iFlow names, header names and Groovy are
  English; agents work better in it; it is portable. The Czech document is translated during extraction. Pavol
  reads the result in English with Czech chat support when needed.

## 5. Sources of truth, in priority order

1. **Pipeline artifacts on disk**: the unpacked SAP standard packages, both the version studied first and the
   current one. Each iFlow as a zip or folder (BPMN XML, manifest, parameters.prop / .propdef, Groovy / XSLT
   resources). Path to be supplied by Pavol; the builder copies or links it as `knowledge/sources/<version>/`
   (ignored or committed, per §10).
2. **The Czech document** from the first analysis (download from where Pavol stored it).
3. **Chat exports**: Claude Code session(s) on version 1, ChatGPT conversation(s) on the update. Extracted with the
   prompt in Appendix A.
4. **SAP documentation and blogs** on the pipeline concept, for terminology and intent only. Not for facts about
   behaviour; the artifacts decide.

Rule: when 2 to 4 contradict 1, the artifact wins and the contradiction is recorded in `pitfalls.md`
(it is usually a version change, and that is valuable).

## 6. Shape of the knowledge base

Lives in the repository under `knowledge/`, and the skill under `.claude/skills/sap-is-pipeline/` is a thin wrapper
(SKILL.md with the loading rules) whose `references/` is a symlink or copy of `knowledge/pipeline/`. If symlinks are a
problem on Windows, the skill folder *is* the knowledge folder and `knowledge/` is a pointer; the builder decides,
as long as there is one copy of the content.

```
knowledge/
  pipeline/
    SKILL.md                    # what the skill is for, when to load what, 1 screen
    overview.md                 # the pipeline in one page: purpose, message path, list of generic iFlows, diagram
    contracts.md                # headers, exchange properties, JMS queues, ProcessDirect endpoints between steps
    partner-directory.md        # what is stored per scenario, key scheme, value types (XSLT, string, binary)
    scenario-contribution.md    # checklist: what a scenario adds (iFlows, PD entries, config), what it must not touch
    naming.md                   # SAP's own naming in the package + placeholders for tenant naming rules
    iflows/
      <generic-iflow-id>.md     # one per generic iFlow: purpose, steps in order, in/out contract, PD reads,
                                #   scripts used, error handling, externalized parameters, extension points,
                                #   version notes
    templates/
      <template-id>.md          # one per SAP scenario template (inbound / outbound / mapping ...): same structure;
                                #   these define what a scenario contributes (see §12.1)
    benchmark/
      questions.md              # ~20 questions with expected answers (Pavol), see §9.5
      sample-ico.json           # synthetic ICO in po-xray output format + expected-proposal.md (see §12.5)
    scripts/
      <script-name>.md          # one per Groovy/XSLT resource that matters: what it does, inputs, outputs, gotchas
    migration/
      po-ico-to-pipeline.md     # procedure: ICO (po-xray output) → scenario spec → proposal → artifacts
      is-iflow-to-pipeline.md   # procedure: point-to-point iFlow → scenario spec → proposal → artifacts
      proposal-template.md      # the document the human approves before generation
    conversion/
      README.md                 # how recipes are written; standard modules table; custom module / Java mapping rules
      <recipe>.md               # one per PO module or pattern, added as migrations happen (part 5)
    versions/
      README.md                 # which SAP version is current, what each version folder holds
      <version>/changelog.md    # diff to the previous version: iFlows added/removed/changed, contract changes
    pitfalls.md                 # lessons learned, contradictions found, things SAP does not document
    glossary.md
  sources/                      # unpacked SAP packages per version (see §10 for git status)
    <version>/
```

Design rules for the content:

- **Current version is primary.** Every file describes the current version. Differences to older versions are
  one-line notes "(v1: was X)" inline, and the full diff is in `versions/<version>/changelog.md`.
- **Cite the artifact.** A statement about behaviour names the iFlow and step, or the script and line, e.g.
  `[Step 2, Content Modifier "Set receiver"]` or `[scripts/SetHeaders.groovy#L40]`. No citation, no fact; it goes
  to `pitfalls.md` as an open question instead.
- **Placeholders for tenant values.** Anything that differs per tenant is written as `{{tenant.<path>}}`, e.g.
  `{{tenant.jms.queue.inbound}}`, `{{tenant.endpoint.outbound}}`, `{{tenant.package.generic}}`. `naming.md` collects
  the full list of placeholders used; that list is the interface to part 2.
- **Checklist form where an agent will act.** `scenario-contribution.md` and the two `migration/` procedures are
  numbered steps with inputs and outputs, not essays; the generator (part 4) implements the same list.
- **Size budget.** `SKILL.md` + `overview.md` + `contracts.md` + `scenario-contribution.md` together under roughly
  4,000 words: that is what an agent loads for a typical migration. Per-iFlow and per-script pages are loaded on
  demand. If a page grows past ~1,500 words, split it.
- **Diagram.** `overview.md` has one Mermaid sequence or flow diagram of the message path through the generic iFlows,
  with queue and endpoint placeholders on the arrows.

## 7. Extraction procedure (how the builder fills it)

Three passes, in this order. The order matters: the truth first, then the reasoning on top of it.

**Pass A, artifacts → structure.** For each generic iFlow in the current version: unpack, read the BPMN, list steps
in order with their type and configuration, read every script it references, extract externalized parameters. Write
`iflows/<id>.md` and `scripts/<name>.md` from that alone. Then write `contracts.md` by following each header and
property from where it is set to where it is read across iFlows, and `partner-directory.md` from every partner
directory lookup. Repeat for the older version only as far as needed for `versions/<v>/changelog.md` (diff the
unpacked trees first; document only what changed). This pass is mechanical and suits a cloud session well if the
sources are in git; otherwise it runs locally.

**Pass B, chats and document → the why.** Run the prompt in Appendix A against each export. It produces a list of
*claims*: short statements with the chat's confidence and the place in the chat. The builder checks every claim
against pass A output: confirmed claims become sentences in the right file (with artifact citation); claims about
intent, rationale or SAP's design choices that cannot be checked are kept, marked `[rationale, from analysis
2026-xx]`; claims that contradict the artifacts go to `pitfalls.md` as "chat said X, artifact shows Y (version
change?)". The Czech document is treated the same way, translated as it is mined.

**Pass C, procedures.** Write `scenario-contribution.md`, both `migration/` procedures and `proposal-template.md`
from passes A and B plus Pavol's practical experience (interview, one question at a time). Seed `conversion/` with
the standard-module table as far as it is already known.

Pass A must be complete before pass B starts. Pass B claims never create a fact without a citation.

## 8. Self-improvement rule

After every migrated scenario (real or rehearsal), the agent that did it appends to the knowledge base before the
work is called done:

- a new or amended **recipe** in `conversion/` for every module or mapping pattern it converted,
- a **pitfall** for every place where the knowledge base was wrong, silent or ambiguous,
- a note in the relevant `iflows/` or `contracts.md` page when it learned something about the pipeline itself.

Each addition is a normal commit with the scenario named in the message (anonymized if customer-specific). The
`migration/` procedures end with this step so it cannot be skipped. A quarterly (or per SAP release) consolidation
pass folds pitfalls into the main pages.

When SAP releases a new pipeline version: unpack to `sources/<new>/`, diff against the previous tree, write
`versions/<new>/changelog.md`, then update the primary pages and the inline "(vN: was X)" notes.

## 9. Done criteria

Part 1 is done when:

1. Every generic iFlow of the current version has an `iflows/` page, every referenced script a `scripts/` page.
2. `contracts.md` and `partner-directory.md` cover every header, property, queue, endpoint and partner directory key
   that appears in the artifacts, each with where it is set and where it is read.
3. `versions/<current>/changelog.md` lists every difference to the previously studied version.
4. `naming.md` lists every `{{tenant.*}}` placeholder used anywhere in the knowledge base.
5. Benchmark: a fresh agent session with only the skill loaded answers a fixed set of about 20 questions (written by
   Pavol before the work starts, kept in `knowledge/pipeline/benchmark.md` with expected answers) and walks through
   `migration/po-ico-to-pipeline.md` for one synthetic ICO, producing a plausible proposal. Pavol judges the result.
6. The Czech document and both chat exports have been mined; nothing in them that is both true and useful is missing.
7. Nothing customer-specific anywhere under `knowledge/`.

## 12. Decisions made during review

Settled by the author after the builder check; Pavol can overrule any of them.

1. **Templates are in scope.** SAP ships the pipeline as generic iFlows plus scenario-side templates (the inbound /
   outbound / mapping iFlows a customer copies per scenario). The templates define what a scenario *is* in artifact
   terms, so `scenario-contribution.md` and part 4 cannot exist without them. Add `templates/<template-id>.md`
   next to `iflows/`, same page structure, and derive the contribution checklist from the templates, not by
   inference from the generic side. Pass A covers both packages. Done criterion §9.1 extends to templates.
2. **Standard pipeline is the subject; deviations live in the tenant profile.** Customers copy the SAP packages so
   they can take SAP updates; the structure is standard, the parameters differ (confirmed for E.ON). The knowledge
   base therefore documents the SAP standard and, for each generic iFlow, its **extension points** (where a customer
   could legitimately add steps). Whether a given tenant did, and how, is tenant data: part 2's profile gets a
   `deviations` section, and the placeholder list in `naming.md` reserves `{{tenant.deviations.*}}` for it. Pass A
   may run a local, uncommitted diff "standard versus customer copy" to discover deviations; results go to the
   profile, never to `knowledge/`.
3. **Scrubbing rule for sources.** Pass A always separates SAP defaults (`.propdef`, template parameter
   definitions) from configured values (`parameters.prop`, configured externalized parameters). Only catalogue
   downloads may be placed under `knowledge/sources/`; a tenant export is used locally for the diff in §12.2 and
   then discarded. Regardless of repository visibility (§10.1), configured values never enter git.
4. **Variants.** Descriptive pages (`iflows/`, `templates/`, `contracts.md`) document every variant present in the
   artifacts. `scenario-contribution.md`, both `migration/` procedures and `proposal-template.md` are written as one
   main path for the variants Pavol names in §10.3, with other variants as clearly marked branches ("if synchronous:
   ..."). The 4,000-word budget in §6 applies to the main path; branches may be moved to `migration/variants.md`
   and loaded on demand.
5. **Synthetic ICO for the benchmark is a part 1 deliverable.** po-xray reads ICOs online, and `testdata/` is
   confidential, so no committable fixture exists. The builder writes one by hand in the po-xray `ico` JSON output
   format (anonymized, derived locally from a real one, with invented system and interface names) and commits it as
   `knowledge/pipeline/benchmark/sample-ico.json` together with the expected proposal. The benchmark session reads
   the file; it needs neither a PO system nor the MCP server. The same fixture later serves part 4 as its first
   test input.
6. **Sources: clean download for git, tenant export for local use only.** The repository is private, so SAP
   packages may be committed under `knowledge/sources/`, but the copies on disk are tenant exports and carry
   E.ON's configured values. Therefore the builder downloads the current pipeline packages fresh from the
   Integration Suite content catalogue (Discover → Integrations, or the SAP Business Accelerator Hub) and commits
   those. The E.ON exports stay local: they feed the deviations diff (§12.2) and later the E.ON tenant profiles
   (part 2). Cloud sessions see only the clean download. If the clean download and the E.ON export differ in
   structure, that difference is recorded in the (local, uncommitted) profile draft, not in `knowledge/`.
7. **Older version: chat-sourced changelog.** The older version's artifacts are gone, so
   `versions/<current>/changelog.md` is built from pass B claims (chats and the Czech document), each entry marked
   `[source: analysis chat, unverified against v1 artifacts]`. Done criterion §9.3 is reduced accordingly: every
   difference the chats establish, not every difference that exists. Where SAP's release notes for the package list
   changes, they are cited as a second source. Should the older package still be obtainable from the catalogue or a
   backup, pass A is run on it and the marks are removed.
8. **No single main path; checklists are decision tables.** Since asynchronous and synchronous both occur, XI and
   IDoc senders always, and XSLT in the partner directory only sometimes, §12.4 is replaced: `scenario-contribution.md`
   and the `migration/` procedures key every step on scenario attributes (quality of service, sender type, mapping
   kind, receiver count) as a table "attribute value → artifact to produce", not as one linear path with branches.
   The proposal template records those attribute values at the top, so the human approves the variant explicitly.
   The §6 size budget for the loaded set rises to about 5,000 words; if a table does not fit, the less common
   variants move to `migration/variants.md`. The attribute set itself is provisional until pass C and is finalized
   with Pavol once the artifacts have been read.

## Appendix A: chat extraction prompt

Use once per export (Claude Code transcript, ChatGPT conversation, the Czech document). Paste the export after the
prompt, or attach it. Works in Claude or ChatGPT.

```
You are mining a long technical conversation about the SAP Integration Suite "pipeline concept"
(the SAP-provided set of generic iFlows for PO-style message processing). Your job is extraction,
not summary.

Produce a numbered list of CLAIMS. A claim is one factual or design statement that the conversation
established, in one or two sentences, in English. Keep the exact technical names as they appear
(iFlow names, header names, exchange property names, JMS queue names, partner directory keys,
Groovy script names, step names).

For every claim give:
- CLAIM: the statement
- KIND: one of fact | rationale | procedure | pitfall | open-question
  (fact = how something behaves; rationale = why SAP or we designed it so; procedure = steps we
  agreed to follow; pitfall = something that bit us or was surprising; open-question = unresolved)
- CONFIDENCE: high | medium | low, as the conversation itself treated it (verified in an artifact
  = high; stated by one side without checking = medium; guessed = low)
- VERSION: which pipeline version the claim is about, if the conversation says; else "unknown"
- WHERE: a short quote (max 15 words) or the turn position so a human can find it

Rules:
- Do not merge claims. One statement per item, even if that gives 200 items.
- Do not add anything the conversation did not say. If something is implied but never stated,
  mark it CONFIDENCE low and KIND open-question.
- Include corrections: when a later turn corrects an earlier one, output the corrected claim and
  add a pitfall claim "earlier we thought X".
- Include every mention of a difference between pipeline versions as its own claim.
- Include every customer-specific value (queue names, URLs, package names) as its own claim with
  KIND fact and the note "[tenant-specific]" so it can be moved to a tenant profile instead of the
  knowledge base.
- Group the output under headings by the generic iFlow or topic the claims belong to; put claims
  that span the whole pipeline under "Cross-cutting".
- At the end, list the technical names (iFlows, scripts, headers, properties, queues, PD keys) you
  saw, each once, as a flat index.

Output Markdown.
```

For a conversation too long for one pass, split it at natural points and run the prompt per part, then run it
once more over the concatenated claim lists with the instruction "merge duplicates, keep the highest confidence,
keep all WHERE references".
