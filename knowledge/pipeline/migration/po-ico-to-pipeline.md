# Migration: PO ICO to pipeline

From one SAP PO Integrated Configuration (ICO) to an approved pipeline scenario on the `2026-06-trial` fact base; attributes per D-025. It reports what the ICO contains and the pipeline needs, without assessing the ICO.

## Inputs

- ICO JSON: `po-xray ico -s <system> -c <component> -f json` (`--system`, `--component`; `--direction` in | out | both, default both, out = the component sends; `--format`, default all; `--output`, default `.`). The file is `icos-<component>.json`: the record `IntegrationInventory` written by `io.poxray.json.Json`, field names = record component names, null and empty fields omitted (an absent `condition` is no condition).
- This knowledge base: scenario-contribution.md, partner-directory.md, conversion/README.md.
- Tenant profile (part 2): not yet available; tenant values stay naming.md placeholders.

## Steps

1. Read the ICO JSON: one `icos[]` entry → the proposal's Source summary; paths as in the model:
   - `icos[].sender`: `party`, `component`, `iface` (`name`, `namespace`), `operations[]`, `channel` (`party`, `component`, `name`);
   - `icos[].receivers[]`: `party`, `component`, `qualityOfService`, `condition` (`text`, `lines[]` with `group`, `left`, `operator`, `right`), `channels[]`, `interfaces[]` (`operation`, `condition`, `mapping`, `targets[]` with `iface` and `multiplicity`, `parameters`);
   - `icos[].dynamicRouting` (`operationSpecific`, `mappings[]`); `icos[].noReceiverBehaviour` (configuration, not an attribute);
   - `channels[]`: `id` (`party`, `component`, `name`), `direction`, `adapter` (`transportProtocol`/`messageProtocol`), `modules[]`;
   - `esr.operationMappings[]` whose `id` equals an `interfaces[].mapping`, with `steps[]`; `esr.messageMappings[]`; `esr.importedArchives[]`; `esr.serviceInterfaces[]` (`operations[].mode`).
2. Derive the attributes: Source summary → one value each by the table below; unresolved → Open questions.
3. Fill migration/proposal-template.md: attribute values, Source summary → every section of the proposal.
4. Obtain human approval: the proposal → Status approved, with name and date. Nothing is generated without it; open questions block it.
5. Produce the artifacts: the approved proposal → what scenario-contribution.md "What a scenario contributes" lists for the approved values, checked against its "What a scenario must not touch".
6. Convert modules and mappings per conversion/README.md: sender and receiver `channels[].modules[]` (`position`, `name`, `type`, `namespace`, `parameters`) and the mapping programs (`esr.operationMappings[].steps[]` with `kind` request | response | fault and `program`: `type` XI_TRAFO message mapping, MAP_ARCHIVE_PRG Java mapping, class in its `program`; `esr.importedArchives[].programs[]` with `kind` javaMapping | class | xslt | javaSource, `mappingApi`, `text`) → one Conversions needed row each, with its recipe.
7. Append to the knowledge base (spec §8, last section): lessons → recipe, pitfall, page note, committed.

## Append to the knowledge base

Spec §8:

- [ ] a new or amended recipe in conversion/ for every module or mapping pattern converted (conversion/README.md);
- [ ] a pitfall in pitfalls.md for every place where this knowledge base was wrong, silent or ambiguous;
- [ ] a note in the relevant iflows/ page or contracts.md for what the migration showed about the pipeline itself.

Each addition is a commit naming the scenario (anonymised if customer-specific). A migration is done only when this step is committed.
